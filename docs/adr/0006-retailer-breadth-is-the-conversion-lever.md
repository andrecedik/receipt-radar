# Retailer breadth is the next priority, and multi-retailer parsing was never SaaS-reserved

**Status:** accepted

Wave-one launch went out (r/selfhosted New Project Megathread comment 2026-09-14, r/grocy 2026-09-17) and the five-day read on 2026-09-22 was: 18 upvotes → ~12 unique repo visitors → 4 stars → **0 image pulls**, with GHCR flat at its baseline of 3. ADR 0002's primary success metric did not move at all; only the reach metrics did.

The r/grocy comments explain the gap, and they point away from the product: **nobody raised install friction** — not the Quick Start, not Docker, not the missing auth on the upload endpoint. Every commenter shops somewhere else (Lidl, Netto, Penny, Rewe, Aldi in Australia, EDEKA, METRO; none at Kaufland). The drop-off is at "visited the repo, did not run it," and the reason given, unprompted and repeatedly, is that the tool only speaks Kaufland.

We decided **retailer breadth is the next build priority**: REWE (shipped), then EDEKA, then Lidl — and, separately, that no ADR ever reserved multi-retailer parsing for the deferred hosted service in the first place.

That second half is a clarification, not a change. `CONTEXT.md` defines **Total Spend Aggregation** as a user's own spend "rolled up across every retailer they shop at and have parsed receipts for" — an MVP, single-user-scope feature that structurally requires more than one parser. What ADR 0001 deferred is **Cross-Retailer Price Comparison**, which needs *many users*, not many parsers, and ADR 0004 already lists parsing as part of the AGPL client. The only thing that ever held parsers back was ADR 0002's sequencing, which put Docker packaging and **Grocy Stock Push** ahead of them; both shipped, so that gate is spent.

**The evidence base is thin and we are saying so.** Five comments and roughly twelve visitors is not validation of anything. This is a re-aim on weak evidence, chosen because the weak evidence all points the same way and because the alternative — building more depth for an audience that is not installing — is worse.

## Ingestion shape: parsed receipts are the base, APIs are an accelerator

Two of the retailer asks point at APIs rather than PDFs: Lidl has a Lidl Plus API (an existing third-party tool, LidlToGrocy, already uses it to push into Grocy), and a commenter offered working details of the Kaufland receipt API, whose JSON carries a `gtin` per line item.

We decided a **Retailer Parser** over a receipt the user exports themselves is always the base integration for a retailer, and a **Receipt Source** built on a vendor API is an accelerator layered on afterwards — never the other way round. A vendor API can be switched off, rate-limited, or have its auth broken by an app update, and none of that is visible or fixable from here; a receipt the user already holds cannot be withdrawn. Building the API path first would make each retailer's support only as durable as someone else's undocumented endpoint, and would leave no fallback when it goes. Building the parser first means the API, when it arrives, is strictly upside: better data (GTINs for barcode-based **Product Mapping**, no manual export step) over a floor that keeps working without it.

## Considered Options

- **Hold ADR 0002's sequencing and build HA Notification Hook next** — the honest reading of 0002's own text, but it deepens the product for an audience that has not installed it; wave two (r/homeassistant) has no reason to convert better than wave one did while the retailer list is unchanged.
- **Take the Kaufland API lead first** (auto-sync, GTIN per line) — genuinely the bigger product jump, and it would upgrade Grocy matching from item-name to barcode. Rejected as a *build* priority because it deepens the single retailer that no commenter shops at, which is the exact axis the funnel says is broken. The DM should go out regardless of that ranking — the lead costs an hour and goes cold, while the build can wait; as of this ADR it is drafted, not sent. The 2026-08-21 no-probing rule stands — accept endpoint details someone else recovered from the real app, never guess endpoints.
- **Lidl via the `lidl-plus` API instead of a PDF parser** — more data for less parsing work, and LidlToGrocy proves the route works. Rejected as the *base* for the reason above: the API is someone else's to revoke, so the parser is what makes Lidl support survive it. Revisit the API as a second ingestion path once the parser exists.
- **Legacy-receipt OCR** (pre-July-2024 Kaufland PDFs, and the Australian Aldi ask, which is paper-only) — rejected: OCR is a large, low-confidence cost serving the smallest ask in the thread, and it widens nothing that a text-layer parser cannot widen more cheaply.
- **Read 0 pulls as the audience bet failing and reconsider the audience itself** (ADR 0002's own revisit clause) — rejected for now. The clause says to revisit "if outreach doesn't produce real installs/usage," and it produced none. But the comments locate the failure at retailer coverage, not at the audience: these are people running Grocy who wanted exactly this and could not use it. Re-aiming coverage is the cheaper test, and it is the one the launch post explicitly asked the thread to decide ("which retailer, and what does their receipt look like").

## Consequences

- ADR 0002's consequence *"Rewe/Edeka/Lidl multi-retailer parsing is not the next priority"* is **superseded by this ADR**. The rest of 0002 stands unchanged: the audience choice, the launch-channel sequencing, and GHCR pull count as the primary success metric.
- **The checkpoint is the whole committed set plus a new post.** REWE, EDEKA and Lidl all ship before the funnel is re-read: the samples are already in hand, each is a parser variant rather than a rewrite, and stopping after the two German-only chains would take the reading just before Lidl — the one retailer in the set that trades outside Germany, and so the only one that tests whether coverage or the addressable audience is the real ceiling. Pull count also cannot move without fresh outreach, so a flat line after merging parsers into a repo nobody is looking at proves nothing: re-read once all three ship *and* wave-three outreach is posted. What that reading governs is a fourth retailer and the audience bet below, not the committed three.
- **If that reading is still flat, ADR 0002 itself is what gets reconsidered** — the audience bet, not the parser count. Three retailers and two launches with zero installs would mean the problem is not coverage.
- **The geographic narrowing in ADR 0002 is not yet relaxed.** REWE and EDEKA are German-only, so they widen the German slice without widening the addressable audience. Lidl is the first retailer in the committed set that trades outside Germany, but its parser will be built against German Lidl receipts — treat any international widening as unproven until a non-DE Lidl receipt has actually been parsed.
- **Renaming is no longer a deferred question.** ADR 0002 deferred it "until this audience bet is validated," on the assumption that waiting is free. It is not: the rename gets more expensive with every pull of the GHCR image, and there are currently none, while the repo, the image path, the Python package and the `kaufland` CLI all say Kaufland for a tool that now parses REWE. The name is also plausibly part of the conversion gap this ADR is about — a reader scanning a megathread for a receipt tool reads `kaufland-receipts` and correctly concludes it is not for them, which is what the thread said in words. Decided separately in its own ADR once a name is chosen.
- **`CONTEXT.md` gains Retailer Parser and Receipt Source**, because "add Lidl" meant two different pieces of work until the distinction had a name.
- **The thread replies are a dependency of this plan, not a courtesy.** The r/grocy comments are drafted but unanswered as of this ADR. The EDEKA samples and regexes that the next parser depends on were offered *in that thread*, by a commenter who already parses EDEKA receipts himself, and the Kaufland API details were offered the same way. Retailer breadth is cheapest when the people who own the sample receipts are still engaged, so posting the replies comes before the EDEKA parser, not after it.
- The README/FAQ needs the canned answer to the barcode-scanner objection raised in the thread — receipts are retroactive and cost nothing at the till, and they carry the price a scanner never captures. Positioning, not architecture; no ADR of its own.
